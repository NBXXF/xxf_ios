# 测试编排（Auto Test Orchestrator）

## 触发场景

- 改完代码后需要自动验证
- 需要定位失败测试的首个有效根因
- 需要在最小范围内做回归验证

## 默认行为

1. 先从仓库中发现测试入口：
   - `Package.swift`
   - `*.xcodeproj`
   - `*.xcworkspace`
   - `Tests/`
   - CI 脚本
   - 现有脚本或文档中的测试命令
2. 优先选择最小测试范围：
   - 受影响测试 target
   - 相邻模块或功能子集
   - 必要时才扩展到更大范围
3. 执行测试，不停留在“建议你运行什么命令”。
4. 失败时优先分析第一个有效失败，而不是被级联错误带偏。
5. 修复后或收敛 root cause 后，重新执行最小相关范围验证。

## 自主执行规则

- 默认直接行动，不先提问。
- 只有在以下情况才升级给开发者澄清：
  - 需要密钥、签名、生产环境配置或敏感凭据
  - 存在多个高风险测试入口且仓库没有明显默认值
  - Xcode scheme 未共享、destination 不唯一，或本机测试前置条件不明确
  - 命令可能改写外部系统或受保护状态
  - 缺少必要工具且安装会改变环境
  - 失败本质上是产品意图不清，而不是技术问题

## 推荐协作顺序

1. 上游可以来自 `xxf-aaa-test-strategy` 的最小必测集，也可以来自 `xxf-aaa-unit-test-writer` 的补测结果。
2. 本 skill 负责把相关验证真正跑起来，并收敛失败根因。
3. 如果验证暴露具体代码风险或回归点，可交给 `xxf-aaa-code-reviewer` 做问题归类。
4. 如果验证结论要转成“能不能放行”，交给 `xxf-aaa-risk-gate`。
5. 如果要把这些规则固化进 CI，再交给 `xxf-aaa-ci-quality-gates`。

## 执行策略

1. 优先复用仓库现有测试约定。
2. 优先可重复、可脚本化、可局部运行的命令。
3. 对 Swift Package，优先 `swift test` 或 `swift test --filter`。
4. 对 Xcode 工程，优先最小化的 `xcodebuild test` 范围。
5. 如果无法安全确定测试入口，先输出候选入口和阻塞原因，再请求最小澄清。
6. 如果没有明显测试 target，至少尝试编译级验证。

## 失败处理

失败时先分类：

1. 编译或配置失败
2. 确定性逻辑失败
3. 环境或依赖失败
4. 不稳定或时序相关失败
5. 与当前任务无关的历史失败

然后输出：

- 首个可执行根因
- 是否与当前改动相关
- 最强的部分验证结论
- 尚未覆盖的风险

## 输出模板

- 测试范围：为什么选这个范围
- 执行命令：实际运行了什么
- 结果：通过 / 失败 / 部分验证
- 首个有效失败：定位与判断
- 残余风险：哪些点还没被证明

## 反模式

- 还没看仓库就让开发者自己选 scheme 或 simulator
- 直接跑全量大测试，忽略最小验证原则
- 把级联失败当成多个独立问题
- 遇到轻微阻塞就把执行责任推回给开发者
- 在 scheme、destination、签名条件不明确时盲跑 `xcodebuild test`
