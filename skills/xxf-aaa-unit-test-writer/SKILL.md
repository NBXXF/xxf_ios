# 单元测试编写（Unit Test Writer）

## 触发场景

- 修复 bug 后需要补回归单测
- 改动涉及边界分支、错误分支或核心纯逻辑
- 现有单测失效，需要自动修复
- 需要补回归单测而不是只停留在建议

## 默认行为

1. 先读取现有测试风格：
   - 测试框架
   - 命名规则
   - 断言风格
   - fixtures / mocks / helpers
   - async 测试约定
2. 识别真正需要证明的行为：
   - bug 复现
   - 边界输入
   - public contract
   - error path
   - 回归风险点
3. 只写最小但有效的测试集：
   - 改动前应该失败
   - 改动后应该通过
4. 运行相关测试并根据结果收敛。

## 自主执行规则

- 默认直接补测试，不先询问。
- 只有在以下情况才升级给开发者：
  - 预期行为从代码和上下文里无法恢复
  - 补测必须修改测试基础设施或架构边界
  - 测试依赖密钥、网络、签名或外部可变状态
  - 现有测试入口无法稳定运行，需要先澄清 scheme、destination 或本机环境前提
  - 当前仓库根本没有可落地的测试 target，新增会变成框架决策
  - 多个调用方表达出互相冲突的行为预期

## 推荐协作顺序

1. 如果用户先问“最小要测哪些”，应先参考 `xxf-aaa-test-strategy` 的输出。
2. 本 skill 负责把关键单元测试真正补出来。
3. 补完后交给 `xxf-aaa-auto-test-orchestrator` 做实际验证，或直接在本 skill 内运行最小相关测试。
4. 如果补测过程中暴露出具体代码缺陷，可交给 `xxf-aaa-code-reviewer` 或实现流程继续深挖。
5. 如果需要判断是否具备放行条件，交给 `xxf-aaa-risk-gate`。

## 选测原则

1. 优先行为测试，不优先实现细节测试。
2. 优先一个能抓住真实风险的精确场景，不堆低信号覆盖率。
3. 优先高风险分支，再考虑次要路径。
4. 能复用现有 helpers / fixtures 就不要新造一套。
5. 对 bug 修复，优先先把 bug 编码成可重复失败用例。

## 质量标准

一个合格的单测应当：

- 本地可重复
- 可读，不需要反向推导生产代码
- setup 最小化
- 断言足够严格，能真实拦住回归
- 不依赖脆弱时序

## 输出模板

- 覆盖行为：这组测试证明了什么
- 变更文件：新增或修改了哪些测试文件
- 执行命令：跑了哪个最小测试范围
- 结果：通过 / 失败 / 部分验证
- 残余缺口：还有哪些风险没有覆盖

## 反模式

- 只追求测试数量或覆盖率数字
- 过度 mock，最后只证明 mock 自己
- 大量断言 private 细节而不是 public observable
- 为了补一个测试引入一整套新测试基础设施
- 在没有可运行验证入口的前提下声称“已自动验证”
