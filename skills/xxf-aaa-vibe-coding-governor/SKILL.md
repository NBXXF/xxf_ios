# Vibe Coding 治理闭环

## 资源来源

- 本 skill 的方法论提炼来源：`https://github.com/NBXXF/vibe-coding-cn/tree/develop/docs`

## 触发场景

- 用户需求模糊，容易直接开写导致返工
- 需要把“看起来对”改成“可验证为对”
- 需要给 AI 协作建立硬门禁与交付证据
- 需要把一次经验沉淀为可复用流程

## 核心原则

1. 问题先于代码：先写清目标、现状、差距、约束、对象、路径。
2. 拼好码优先：优先复用成熟实现，业务层只做编排、适配、组合。
3. AI 不能自证正确：以测试、CI、脚本、类型、schema、清单做第三方判定。
4. 最小改动优先：只改当前目标路径，不顺手重构。
5. 证据化交付：结论必须绑定命令、输出、diff、风险与回滚路径。

## 标准工作流

### 1. 任务定义卡（先写再做）

最小要素：

- 目标：要达成什么可观察结果
- 边界：明确不改什么
- 验收标准：通过条件（可脚本化）
- 约束：时间、技术栈、兼容性、安全
- 风险：潜在回归面

### 2. 上下文扫描

按顺序读取：

1. 根 `README.md` / `AGENTS.md`
2. 目标模块文档与现有实现
3. 测试入口、构建入口、CI 入口
4. 历史变更与已知限制

禁止在上下文未建立前直接实现。

### 3. 方案选择（拼好码优先）

决策顺序：

1. 先复用已有模块/成熟依赖
2. 无法复用时再新增最小实现
3. 新增实现必须说明为何不能复用

### 4. 执行与收敛

- 小步提交：每步可验证
- 单次改动只处理一个主问题
- 每步都运行最小相关验证
- 失败时回到“假设-验证-修正”循环

### 5. 硬门禁验证

至少覆盖：

- 代码门禁：语法、lint、核心测试
- 结构门禁：边界未破坏、无重复入口
- 运行门禁：可按文档启动/执行
- 文档门禁：行为变化已同步说明

### 6. 证据化交付

最终交付至少包含：

- 改了什么（文件与行为）
- 如何验证（命令 + 结果）
- 残余风险与影响范围
- 回滚策略或缓释建议

## 输出模板

1. 任务定义卡
2. 实施摘要
3. 验证证据
4. 风险结论（Block / Warn / Pass）
5. 后续沉淀项
