# 架构评审（Architecture Review）

## 触发场景

- 评审新模块设计是否符合现有架构
- 发现 View/VC 直接调用底层实现、跨层依赖
- 评估重构方案和技术债治理优先级

## 审查清单

1. 分层边界是否清晰：UI -> Domain -> Infra 单向依赖。
2. 抽象是否稳定：业务是否依赖抽象层而非具体实现。
3. 职责是否单一：是否出现 God Object / 超大文件。
4. 模块耦合是否可控：是否存在循环依赖、隐式全局状态。
5. 可替换性是否成立：Provider/Adapter 是否真正可替换。

## 输出模板

- 结论：通过 / 有条件通过 / 不通过
- 高风险问题（必须修复）
- 中风险问题（建议迭代修复）
- 低风险问题（风格与可维护性）
- 建议改造步骤（按优先级）

## 反模式

- 仅给“好/不好”结论，不给定位与修复路径。
- 只看语法和风格，不看依赖方向与职责边界。
